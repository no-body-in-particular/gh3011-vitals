# The GH3011, as this code drives it

A reflectance photoplethysmography sensor on the l009 watch: three LED drivers, one photodiode, a
24-bit converter, at i2c address `0x14` on bus 2 behind `/dev/gh_tools`. This file describes the
part, how this software drives it, and where that differs from the vendor's.

Our code replaces the vendor's `gh3011_service` in the same init slot. **Heart rate, wear detection
and wrist temperature work and are published.** Blood pressure is uncalibrated and reported only
when the pulse shape supports it. Saturation is not measurable on this part; the one section below
says why, and the code for it has been removed.

## Reaching the part

    /dev/gh_tools

    ioctl  0xc0084704   i2c passthrough, an i2c_rdwr_ioctl_data of struct msg
    ioctl  0x40044702   power, 1 or 0
    ioctl  0x40044707   interrupt enable, 1 or 0
    ioctl  0x00004701   wait for an interrupt, blocking
    ioctl  0x40044706   driver init
    ioctl  0x40184709   publish a result to the framework's sensor

A register write is a four-byte message: two bytes of big-endian address, two of value. A read is a
two-message transfer, the address written and then two bytes read back. Some writes are three bytes
- a command, described below.

Two cautions, both learned expensively:

**Read the chip id alongside anything that matters.** `0x0028` reads `0x0031`. When it does not, the
passthrough is returning the previous read's value rather than register contents, and everything
read in that window is fiction rather than data.

**Time the interrupt wait before trusting it.** `0x00004701` returns success without an interrupt
when the part is not configured - in about a second out of a twenty second window, and identically
with the interrupt disabled. A wait that returns early did not wait.

## Commands

Written as `dd dd <cmd>`, three bytes, to no register:

    c0   halt
    c1   start
    c3   arm a read of a running part
    c4   stop

A running part returns zero for every register in the space until `c3` is issued.

## Registers

### Timing

| register | meaning |
|---|---|
| `0x0016` | sample rate divisor: rate = 32768 / value. `051e` is 25 Hz, `0147` is 100 Hz |
| `0x0002` | written `fe30` before an auto-detect start; the part alters what is written |

Green runs at 25 Hz and red/infrared at 100. A heart rate needs no more than 25 - 200 bpm is
3.3 Hz - but the systolic upstroke behind a blood pressure is four samples at that rate, so only
the pressure asks for 100.

### Light

| register | meaning |
|---|---|
| `0x0080` | LED drive, per slot |
| `0x0082` | LED drive, per slot |
| `0x0084` | integration and drive selection |
| `0x0118` | gain. `2828` for a measurement, `1f69` in the auto-detect table |
| `0x011a` | gain, second channel |
| `0x0136` | slot LED current |
| `0x0186` | slot enable |

### Slots and sampling

| register | meaning |
|---|---|
| `0x0100`-`0x0116` | per-slot ADC windows, six pairs |
| `0x011c`-`0x0120` | per-slot thresholds |
| `0x0126`, `0x0128` | slot configuration |
| `0x012a`, `0x012c` | slot timing |
| `0x0130`-`0x0134` | per-slot LED selection |
| `0x0180`, `0x0182` | analogue front end |
| `0x018a`, `0x018c`, `0x0194` | trims, read then written back modified |

### Data and status

| register | meaning |
|---|---|
| `0x004a` | FIFO level, counted in three-byte samples |
| `0xaaaa` | the FIFO, three bytes big-endian per sample |
| `0x0008` | interrupt status. Bit 0 new data, bit 4 wear event, `0x20` chip reset |
| `0x0028` | chip id, `0x0031` |
| `0x0022` | bit 0 is set during init |
| `0x0020` | cleared during init |
| `0x0064`, `0x006a`, `0x006c` | an OTP window: address into `0x0064`, pulse `0x006a` with 1 then 0, read the word from `0x006c` |

`0x004a` counts samples and not frames. Two channels are interleaved, so a frame is two samples and
an odd level is half a frame.

### 0x0136, the LED drive

Two fields in one register: the **low byte drives channel 1 and the high byte channel 2**. Measured
with the current loop frozen, as the level above the 3145728 pedestal:

| low byte | ch1 level | high byte | ch2 level |
|---|---|---|---|
| 0x08 | 64,867 | 0x00 | 64,850 |
| 0x10 | 195,933 | 0x0d | 326,895 |
| 0x20 | 326,974 | 0x1a | 588,781 |
| 0x30 | 457,974 | 0x7f | 1,899,082 |
| 0x40 | 588,997 | | |
| 0x60 | 862,458 | | |

So `level ~= 65536 + (byte / 0x10) * 131072`, linear and independent per channel, in steps of
0x20000. It was found by sweeping with the current loop frozen and reading the level rather than the
raw DC: without freezing, the loop compensates for the extra light by backing the current off and
the DC lands within half a percent of where it started whatever the LEDs are told, which is why an
earlier sweep concluded the register did nothing.

**It also decides whether the two channels are a wavelength pair**, and it is a one-shot rather than
a level. The shipped configuration leaves it at zero where Goodix's reference array sets `0x0110`,
and the difference is `ac2/ac1` of 1.0 against 2.2 - the whole difference between two channels
carrying the same information and two carrying different information. Written once after the start
sequence and committed with `dd dd c1`, the pairing holds for the pass even though the current loop
writes zero over it on every adjustment afterwards. Written on every adjustment instead, the light
comes up so far that the loop walks to its floor. Written after the first current write rather than
before it, the pairing never takes at all. On this part the order of writes carries as much as their
values, and this register is the clearest case of it.

### Wear detection

| register | meaning |
|---|---|
| `0x00c0` | bit 0 enables the detector, bit 8 is the answer: clear means on a wrist |
| `0x00c2`, `0x00c6` | per-channel maximum, `ffff` |
| `0x00c4`, `0x00c8` | per-channel threshold. `034b` for the rate mode, `0528` for saturation |
| `0x00ca`, `0x00cc` | detector timing |
| `0x00ce`, `0x00d4` | detector threshold. `0251` for the rate mode, `042e` for saturation |
| `0x00d8`, `0x00dc` | detector configuration |
| `0x00d0`, `0x00d6`, `0x00da`, `0x00de` | zero |

The vendor's configuration table gives the enable's address as `0x10c0`. That is `0x00c0` with a
flag in the top nibble which this passthrough does not decode; written there it does nothing and
reads back zero. Write `0x00c0`.

## Starting the part

The same shape for a measurement and for a wear check, and neither works without all of it.

1. Power on, then halt.
2. Read the id, the rate and the status.
3. Write `0x0182` and `0x0180`, then read three OTP words through the `0x0064` window - `0x20`,
   `0x22` and `0x24`. Nothing visible is done with them; they are trims the part applies itself.
4. Read and write back `0x0194`, `0x018a`, and write `0x018c`.
5. Clear `0x0020`, and set bit 0 of `0x0022` by read-modify-write.
6. Stop.
7. Halt, and write the configuration table for the mode.
8. **Write six of those registers again with different values.** The table is most of the
   configuration and not all of it, and a part configured only from the table never produces an
   interrupt. For the auto-detect mode: `0x0084` = `0020`, `0x0118` = `2828`, `0x0136` = `0d20`,
   `0x0080` = `0205`, `0x0082` = `00c2`, `0x0186` = `0001`.
9. Write `0x00c0` = `0001` and `0x0002` = `fe30`.
10. Start.

`adtwear.c` performs exactly this; `seq.h` holds the equivalent for a measurement, generated from a
capture rather than transcribed.

## Reading a measurement

Poll `0x004a` for the FIFO level and read `0xaaaa`. Do not enable the interrupt for this: the
kernel driver services the part and drains the FIFO before userspace can, so an enabled interrupt
costs the data it was meant to announce.

Each sample is a 24-bit count with a large pedestal. The pedestal is not a constant - it is
`floor(dc / 0x100000) * 0x100000` for that channel, and treating it as a fixed number was wrong by
a factor that varied with the LED current.

## Reading a wear event

The opposite: the wear answer only exists as an interrupt.

Arm the detector as above, then block on the wait ioctl. When it returns, halt and read `0x00c0`.
Bit 8 clear means on a wrist. Do not require bit 4 of `0x0008` first - the kernel's own handler
reads and clears the status before userspace gets there, so testing it discards good answers.

A window that closes with no interrupt means the watch is not being worn. Measured on this part:
the event arrives in about a second on a wrist including a still one, and not at all off it, five
runs each way with no overlap. Handling the watch off the wrist does fire it, which is correct -
skin on the sensor is skin on the sensor.

## How this software is put together

Three programs and a socket.

`ppgd` does one measurement and exits. It configures the part, polls the FIFO, and prints a line
of fields - rate, the DC and AC of both channels, the ratio, a pressure when the pulse shape
supports one, and the confidence behind each. Everything that reads a waveform is in here, and it
holds no state between runs beyond an optional previous rate to help it choose between two
candidate frequencies on a moving wrist.

`adtwear` answers one question - is this on a wrist - and exits. It arms the chip's detector and
waits for the interrupt.

`vitalsd` is the only long-lived part. It runs in the init slot the vendor's daemon used, listens
on an abstract unix socket named `watchvitals`, and answers three requests by running the other
two as helpers:

    ->  hr            green LED, heart rate
    ->  spo2          red and infrared, adds the ratio and the pulse shape
    ->  wear          the wear detector alone, no measurement

    <-  hr=49 spread=2 hz=24.9 ... r=0.706 sbp=113 dbp=69 conf=0.82 temp=32.6
    <-  hr=0 reason=no_agreement
    <-  worn=1 adt=1

The helpers are separate processes rather than functions because the measurement needs
`/dev/gh_tools` to itself and takes the better part of a minute; a daemon holding that open cannot
also hand it to something else, and a crash in a measurement should not take the socket with it.

A refusal is a normal answer and says why. `weak=1` on a ratio means there was too little pulse
behind it to divide by; `tracked=1` on a rate means the windows disagreed and the previous rate
chose between them; `reason=not_worn` means the wear check answered before any LED was lit.

The client is an Android launcher which speaks to that socket and knows nothing about the sensor
beyond those three words.

### How a rate is arrived at

Six-second windows, a Goertzel filter over the plausible band, and the magnitudes averaged. A rate
is published when the windows agree; when they disagree the previous rate breaks the tie, with
asymmetric bounds - a wrist can speed up faster than it slows down. Green carries the rate because
the physics is not close: haemoglobin absorbs green strongly, and measured on this part green
swings 200 to 900 counts where red manages 1 to 80. Green also only reaches the surface
capillaries, which is what makes it better under motion - deep tissue moves, shallow capillaries
move less.

Confidence is a Gaussian probability that the true rate lies within tolerance of the estimate,
from the spread across windows, with the standard error floored so a lucky pair of agreeing
windows cannot claim certainty.

## What the measurements are worth

| | how it was checked | result |
|---|---|---|
| heart rate | against a cuff's pulse readout, and against the vendor's own daemon on the same wrist minutes apart | about +1 bpm, three of four measurements within two |
| wear detection | fifty runs on and off a wrist | worn within about a second every time on, silence every time off, no overlap |
| wrist temperature | a thermopile, against a room and a wrist | reads 34.6 on a wrist against 26.5 on a table; it is a wrist and not a core temperature |
| blood pressure | against thirty cuff readings over two days | tracks poorly; see the last section |
| saturation | five breath-hold runs against a finger meter | not measurable on this part; removed |

### Heart rate

This is the one worth trusting. Compared against the vendor's daemon on the same wrist minutes
apart it read 46 to 52 where the vendor read 49, and against a cuff's own pulse figure it sits
about a beat high. It refuses rather than guesses: when the six-second windows disagree it returns
`hr=0 reason=no_agreement`, which is what a moving wrist looks like, and roughly what the vendor
does in the same situation.

### Blood pressure

**It withholds far more often than it reports, and that is the gate working.** A worked example
worth keeping: the pressure stopped appearing one evening and three hours went into bisecting the
commits that had landed that day. The control that should have been run first settled it in one
measurement - the *oldest* build, from before any of those commits, also returned nothing. The same
binary had reported 115/71 two hours earlier on the same wrist. What had changed was the wearer's
pulse shape, not the software: the augmentation index had gone negative, which is what the code's
own note predicts when the reflected point lands in baseline drift.

So when a pressure disappears, measure an old build before reading a diff.


Uncalibrated and, more importantly, insensitive. Thirty cuff readings taken alongside it spanned
94/66 to 121/73, and the estimate stayed near 114 systolic throughout - so it is not a pressure
that is offset by a constant, it is a pressure that barely moves. It is published only when the
pulse shape behind it is physiological - an upstroke between 80 and 250 ms and a positive
augmentation index - and both numbers are withheld when it is not, because half a pressure is not
a reading. Treat it as a shape metric with pressure-like units rather than a measurement of
anyone's blood pressure.

### Motion

Green is used for the rate partly because it survives movement better - it only reaches the
surface capillaries, and deep tissue moves more than shallow tissue does. Beyond that the
defences are a spectral purity test, which rejects a window whose peak is not clearly a peak, and
an asymmetric tie-break against the previous rate. None of this makes a reading during vigorous
movement trustworthy; it makes the code decline one.

### A caution

This is a reverse-engineered driver for an undocumented part in a cheap watch, checked against a
consumer blood-pressure cuff. It is not a medical device and nothing here was validated against
one. The heart rate is good enough to be interesting; the rest is recorded honestly so that
nobody has to rediscover which parts are not.

## Where this differs from the vendor's software

Both drive the same part through the same driver. What follows is what a capture of their daemon on
the wire, and their binary, showed them doing differently.

### Their configuration, and how close it is to ours

`docs/vendor-spo2-writes.txt` has all 47 of their writes and `docs/vendor-spo2-ioctls.txt` the call
sequence around them, captured with an `LD_PRELOAD` i2c tap on their daemon.

Diffed mechanically against ours - both captured the same way, both mid-measurement, reads taken
three at a time so a stale bus echo could not pass for a register - **162 registers compared and two
differ**:

| register | vendor | ours | |
|---|---|---|---|
| `0x0118` / `0x0122` | `4f46` | `2323` | the two logic channels' LED currents |
| `0x0100` | `f530` | `ea60` | unexplained; see below |

Everything else matches, including `0x0130`, `0x0132`, `0x0134`, `0x0186` and `0x0136` - so an
earlier table here listing those as differences was describing a heart rate run rather than a
saturation one, and is wrong.

`0x0118` is **not a gain**, which several notes in this file used to call it. Goodix's own init
config names it: two bytes, one per logic channel, at 400 µA a step, with the TIA gains as a
separate field this code has never touched. That is why one code step moves the DC by about a
quarter and why the bytes behave per-channel.

Both loops start in the same place - `0x9055`, `0x2828`, `0x9055` - and then theirs rises, `0x4f44`
to `0x4f4c` to `0x564c`, moving the two bytes independently. Ours used to take one step down and
stop, because the threshold it compared against sat a few hundred counts from where this wrist
settles, so it hunted at the boundary and never converged; every change restarts the analysis
window, and a thirty second pass could end with nothing settled in it. It now uses a deadband with
separate raise and stop thresholds and a hard cap on changes per pass.

`0x0100` reads `f530` for them and `ea60` for us on three consecutive dumps each. It is not write
ordering - from the wire both write `0x0100 = f530` and then `0x0016 = 0147`, one write each, same
order - nor the trailing slot block, nor the current: frozen at three different values it still
reads `ea60`. As signed values ours is exactly twice theirs. That is where it stands.

### How they actually read it

The i2c tap was attached to their daemon and a measurement triggered. It answers the question the
register dump could not, because what they do differently is mostly not registers.

    IOCTL 00004701   wait for the interrupt      blocks, and returns when data is ready
    R 0008 = 0002    status: new data
    IOCTL 825a470a   read 602 bytes of samples   _IOR('G', 0x0a, 602)
    R 0122           the applied LED current, read back - their loop moves it, 9055 -> 4f55
    W dd dd c3       arm the next read
    IOCTL 40184709   publish the result

Three things in that loop we do not do at all.

**They wait on the interrupt and it works.** Ours returns success immediately without an interrupt,
which is why the measurement path polls the FIFO instead - documented above as a gap with no known
cause. Theirs blocks properly, so whatever arms it is in the startup below rather than absent from
the hardware.

**They read samples through the driver, not over the passthrough.** `0x825a470a` returns 602 bytes
in one call. We read the FIFO register in three-byte samples over i2c, on a bus that returns the
previous value often enough to have invented three separate conclusions in this file.

**There is a command we did not know about.** `W dd dd a1`, issued once between the start and the
first sample read. Our set was c0, c1, c3, c4.

### What the vendor actually does about movement: nothing to the waveform

The section above, and the commit that added it, said their ratio is motion-compensated and ours is
not. That was inferred from a function signature - `HBD_Spo2CalculateByFifoIntDbgRawdataInnerUse`
takes the g-sensor FIFO as its first argument - and the inference was wrong. The signature is real.
What they do with the buffer is not compensation.

Followed through the binary, the accelerometer enters at one place and leaves at one place.

**Ingestion.** The algorithm entry at `0x18f38` calls `FUN_00016c04(gs_buf, gs_len, 1 << sens)` with
the sensitivity from `__GS_SENSITIVITY_CONFIG__`. That function walks the FIFO three shorts at a
time, divides each axis by the scale, takes `sqrt(x^2 + y^2 + z^2)` - the **magnitude**, the
rotation-invariant quantity - and folds it into five words by Welford's algorithm:

    [0]  M2, the running sum of squared deviations
    [1]  running mean
    [2]  max
    [3]  min
    [4]  range, max - min

That is the entire representation. The individual axes are not kept, the time series is not kept,
and nothing is retained that could describe the shape of an artefact.

**Classification.** `FUN_00017820` turns those five words into one of six levels:

    M2 <= thr_lo                 ->  1 if (max - min) < thr_range else 2      still
    thr_lo < M2 <= thr_hi        ->  4, or 8 if mean >= thr_mean              moderate
    M2 > thr_hi                  ->  0x10 if max < thr_max else 0x20          heavy

The five thresholds are host-settable through the parameter setter at `FUN_000151e8`, which writes
them at offsets 0, 2, 4, 6, 8 and 0xa of a table whose pointer lives in .bss - so their values are
not in the image and an exact clone of the classifier is not available from the binary alone.

**Consumption.** `FUN_00017890` is the only caller. It branches on the level and runs a dwell timer:
while the wearer stays in a level, a counter accumulates the elapsed time, and when it passes a
threshold in whole seconds the algorithm copies a fresh set of per-channel values into its working
state and resets the counter. In other words the motion level decides *when to re-baseline*, not
what to subtract.

Counting the readers is the shortest proof. Exactly four functions touch the statistics: the one
that writes them, the classifier, that dwell machine, and a reset. The accelerometer never meets
the optical waveform.

#### So the thing to implement is not what was attempted

Three versions of time-domain cancellation were written against this file and all three made a worn
measurement worse; `motion_clean` in `ppgd.c` carries the numbers. They were the wrong shape of
answer, and this is why. The vendor is not cancelling an artefact out of the pulse - they are
deciding whether to believe the pulse at all, and when to start again.

That is the same family as what this code already does with `motion=` and `swing=`, so the gap is
narrower than it looked. What theirs has and ours does not is the descriptor set - a variance rather
than a median of per-burst magnitudes, plus min, max and range - and the dwell, so that a level has
to persist before it counts as a change of state.

One thing that fell out of reading the reset: `FUN_000172b8` derives the timing from register
`0x0016` as `0x8000 / 327`, rounded to a multiple of 25, which is **100 Hz**. Both sides sample at
the same rate, which retires the last version of the "they run at 25 Hz" idea for good.

### The host parameters, read out of the daemon

Everything past register `0x1fff` is a library parameter rather than a chip register. That was
guessed at earlier from readbacks returning zero; it is now exact. `FUN_00017198` walks the
configuration array the daemon hands the library, and splits it on one constant:

    id  > 0x1fff  ->  FUN_000151e8, a host-side parameter setter
    id <= 0x1fff  ->  written to the part over i2c, read back and verified

`DAT_00017208` holds that constant and it is `0x1fff`.

The array itself was found by its contents rather than by chasing pointers - two attempts at the
GOT arithmetic produced a "table" that decoded as Thumb code and another that pointed into the
string section, so the wire capture was used as a signature instead. Entries 23 to 69 match the
saturation writes recorded on the bus exactly, which is what makes the rest of it trustworthy.

Past the registers, this watch's saturation configuration carries:

    0x2030..0x2035    three 32-bit values   -10223, -305835, 1134171
    0x2a00            0x00ff
    0x2a02..0x2a15    ten 32-bit values     60000 38000 58000 40000 10000
                                            60000 38000 58000 40000 14000
    0x2a16, 0x2a17    0x0101, 0x0602
    0x2b03            1
    0x2b07, 0x2b0c    20, 20
    0x2b0f            30

**The first three are the saturation curve for this watch.** They are the override for the
coefficients whose defaults - 0.0, -25.0 and 110.0 - the initialiser at `0x1f8c0` writes, and at a
scale of ten thousand they give

    SpO2 = -1.0223 R^2 - 30.5835 R + 113.4171

Their daemon reported 97% on this wrist, and inverting that curve puts their R at **0.527**. The
default line would have put it at 0.52, so the two agree about where their ratio sits, and the
number stands whichever curve is used.

**The ten after them are the current loop's target levels**, five per channel, in counts above the
pedestal. Read against what the loop in `ppgd.c` was doing:

    60000   the rail to hurry away from
    58000   ceiling
    40000   floor for raising
    38000   target
    10000 / 14000   the two channels' minimum usable levels

The band this file had guessed - 0.55 and 0.88 of a 64,852 span, or 35,669 and 57,070 - was close
enough to work and low enough to settle around 32,500, under their floor. Using their numbers takes
the amplitudes from 75 counts to between 96 and 447 on the same wrist, with the ratio holding
between 0.94 and 1.17 through movement that a few hours earlier would have produced nothing at all.

The parameter setter is two switches, biased by `-0x2A00` and `-0x2B00`, so a case number is the
id's low byte. Cases 2, 4, 6 ... 0x14 of the first share one handler - ids `0x2A02` to `0x2A14`,
the ten gain levels above, which confirms that block from the other direction.

**The classifier's thresholds are ids `0x2A36` to `0x2A3B`**: six consecutive cases writing six
consecutive offsets through the same base pointer, the one `FUN_00017820` reads its five thresholds
from. This watch's array does not contain them. It sets `0x2030`-`0x2035`, `0x2a00`, `0x2a02`-
`0x2a17`, and `0x2b03`, `0x2b07`, `0x2b0c`, `0x2b0f` - and nothing in the `0x2A36` range - so the
library's own defaults are what classify movement here.

That also retires a guess made a few paragraphs ago in an earlier pass: `0x2b07`, `0x2b0c` and
`0x2b0f` at 20, 20 and 30 are *not* the motion thresholds. They are cases 7, 0xc and 0xf of the
second switch, and each writes its own separate global.

## Saturation: not measurable here

The part is specified for SpO2 and a red LED is fitted, but neither this software nor the vendor's
can measure one, and the reason is the sensor rather than the arithmetic. Five breath-hold runs
against a finger meter say so, the last with every prerequisite met - a genuine wavelength pair
(`ac2/ac1` of 2.1 to 2.8, where the shipped configuration gives 1.0 because `0x0136` is left at zero
against the reference's `0x0110`), the vendor's own scale (our R of 0.43 against their 0.496 for the
98% a meter agrees with), firm contact, a still wearer, and a twelve point desaturation: R stayed
inside 0.119 where twelve points demanded 0.43 to 0.82, and wandered independently of the wearer's
breathing. Six formulations were then tried offline against paired raw captures spanning a further
hold - `band_amp` as this code computes it, the second harmonic, peak-to-trough, log-ratio, a
per-beat median, and no pedestal at all - and none peaks during the hold; the three time-domain
forms, which need no frequency estimate, move about a third of what is required. The vendor's own
daemon, run through the same test with their curve and coefficients, reported exactly 98 in 189 of
196 reports, and `RUN_MODE_SPO2_DET` sits behind a flag that is zero on this watch with the sensor
HAL only ever sending commands 4, 5 and 6 - so nothing on this product has ever asked for a
saturation, which reads as a decision rather than an oversight. The cause is in the datasheet: three
LED drivers and **one photodiode**, and the library confirms two logic channels permuted over three
physical LEDs. Wrist oximetry needs several photodiodes at different spacings to separate arterial
from venous pulsation and to correct optical path length; with one detector there are two numbers
and more than two unknowns, and what the ratio measures is a venous-and-arterial mixture - stable,
repeatable to 0.004 at rest, on the right scale, and inert. The captures are kept under `docs/data/`
with `tools/gh3011/ratio-lab.py`, which reproduces this code's own ratio before offering an opinion,
so a seventh idea can be tested against a real desaturation without asking a wearer for anything.

## The route this replaced, and why it is gone

Before the daemon existed the launcher read this chip from Java, underneath the sensor HAL and
through the vendor's own library. That code has been deleted; what it established is here,
because it is why the daemon is shaped the way it is.

### The sensor HAL does not deliver

During a measurement the framework shows the sensor activated and connected, and then sits at
`First flush pending` for the whole window without producing a single sample:

    gh30x_sensor  handle=0x00000008, active-count=1, connections=1
    gh30x_sensor | status: First flush pending | pending flush events 0
    last=< 60.0,120.0, 79.0>        unchanged across 29 s and all ten samples taken

That stale triple is the reason readings were identical for hours, and the reason `com.ic.work`
reported high, low, heart and oxygen all as zero: it is handed nothing, so it has nothing to
report. Neither the wear check nor its work queue was ever the cause - both were patched, and
with the wear flag forced true on a worn watch the zeros survived.

The same applies to the thermometer: `GXTS02S` in the platform sensor list is a mirror sitting
at `last=<0.0,0.0,0.0>`, and `registerListener` on it returns that for ever.

### The driver underneath is fine

Reading `/dev/input/event1` across the same measurement gives a value every second on a worn
watch:

    REL_RX  0x395c -> 57 bpm,  92 %     sensor settling
    REL_RX  0x3916 -> 57 bpm,  22 %
    REL_RX  0x3a50 -> 58 bpm,  80 %
    REL_RX  0x3b64 -> 59 bpm, 100 %     converged, and steady to the end

So a reading is two bytes packed into one `REL_RX`: heart rate high, saturation low. `REL_RZ` is
a once-a-second progress tick (`0x0101`, `0x0201` ... `0x1d01`) and carries no measurement. The
node is world readable, `crwxrwxrwx`.

Blood pressure is not in that stream. The HAL's three-value event has one, so the vendor's
library computes it above the driver.

### Only the vendor could start it, and only in the wrong mode

Nothing in userspace could start the sensor: `goodix_health` exposes no sysfs control, there is
no character device, and the i2c protocol is the vendor's. So the measurement had to be started
by `com.ic.work` through the HAL - the piece that wedges - and only restarting that service
cleared it. Three times in two days, each costing hours of pressure and saturation while the
driver went on producing a pulse perfectly well.

`libICJniUtils.so` exports `enableSPO2` as a GLOBAL symbol with no
`Java_com_ic_jni_ICJniUtils_` wrapper, so it cannot be reached from Java however the class is
declared; a small JNI shim that dlopened the library and called it directly was the way in.
`enablePPG`, which *is* wrapped, starts the chip in heart rate mode only - `event ppg 59 ,
spo2 0 , weared 1` on every sample of a full window, which is what made the vendor's service
look indispensable.

Activating through the HAL is what selected saturation mode: `command, GH_30X gh30x_Spo2Start`
is a string in `sensors.sl8521e.so`, not in `libICJniUtils.so`. So the arrangement was to
register a listener that was never expected to hear anything, purely for the activation, and
read the samples off the input device instead.

### Why none of that is needed now

This daemon talks to the part over i2c itself, in the init slot the vendor's daemon occupied.
There is no HAL in the path to wedge, no service to restart, and no library to borrow an
undocumented entry point from. The last thing the vendor's library was still used for was
reading the thermometer, and the `temp` request replaced that too.

One thing did survive the deletion and is worth keeping in view: the pressures were the only
measurement that came from above the driver, computed inside `getHighBloodPressure` during the
vendor's own measurement. This code derives them from the pulse shape instead, which is a
different method reaching a similar number, and `## What the measurements are worth` above is
the honest account of what that is worth.

## Why the pressure does not track, measured

The shape behind the pressure is now reported with a measure of whether the beats agreed about it:
`sutmed` is the upstroke as the individual beats measured it, `sutmad` how far they sat from that,
`sutn` how many were measured. The pressure itself still uses the ensemble figure.

That measure is real. Over 108 archived recordings replayed offline, it predicts how far the
ensemble sits from what the beats actually said:

    sutmad     n    ensemble differs from the beats by
    0-20      25    6.8 ms
    21-40     12    23.5 ms
    41-80     22    48.1 ms
    81+       12    95.3 ms

So a pass can now say whether its own beats agreed, which they often do not.

Two things were tried on the strength of it and neither is worth having. Using the per-beat median
instead of the ensemble made the published pressure slightly *less* consistent - standard deviation
5.43 mmHg against 5.29. Publishing only where the beats agreed, `sutmad <= 40`, tightened the range
from 32.6 to 25.6 mmHg and threw away two thirds of the readings to do it.

The reason both failed is in the arithmetic. Decomposing `sbp = 100 + 0.28*bpm - 0.055*sut + 11*ai`
across the 71 recordings that produced a pressure:

    0.28*bpm      sd 3.62 mmHg
    -0.055*sut    sd 2.84 mmHg
    11*ai         sd 2.84 mmHg
    total         sd 5.29 mmHg, range 32.6

The largest single source of movement is the heart rate, not the shape. The estimate's spread is
about the size of the real variation - the cuff spanned 94 to 121 systolic over the same two days,
27 mmHg - so it is not that the number fails to move. It moves about the right amount and not in
step, which is a different problem, and the earlier cuff comparison is the direct evidence: the
estimate sat near 114 whether the wearer was at 105 or at 120.

A more consistent upstroke cannot fix that. What would be needed is a calibration against paired
cuff readings, and the sensitivity to check whether this formula can track a real change at all -
neither of which a tighter shape provides. The agreement measure stays because it is cheap and
says something true; the estimator and the gate do not, because they were measured and did not
help.
